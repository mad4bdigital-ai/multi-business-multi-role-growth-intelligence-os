# Platform Growth Operating Model

## 1. Purpose

The shared asset fabric should not only make the platform configurable. It should create a compounding growth system in which each successful tenant/user interaction improves discoverability, readiness, personalization, reusable patterns, and platform quality without compromising isolation or governance.

## 2. Growth flywheel

```text
Shared assets reduce setup friction
→ more users reach a ready workflow
→ more effective manifests and outcomes are observed
→ recommendations and gaps become better grounded
→ users adopt better profiles/preferences/variants
→ successful scoped improvements are certified
→ reusable platform candidates improve shared assets
→ future users receive better defaults
```

The flywheel depends on verified outcomes, not raw engagement.

## 3. Growth layers

### Layer 1 — Activation growth

Goal: move users from membership to first verified value.

Levers:

- shared catalog;
- readiness visibility;
- credential/setup guidance;
- three prioritized recovery actions;
- default composition templates;
- role/activity-aware recommendations.

Metrics:

- time to first shared ready asset;
- first verified execution;
- activation blockers by type;
- connection/install completion;
- first-result quality.

### Layer 2 — User productivity growth

Goal: make each user faster and more successful over time.

Levers:

- personal preferences;
- workflow/agent ranking;
- optional personal variants;
- learned but transparent recommendations;
- reduced repeated setup and decision friction.

Metrics:

- successful tasks per active user;
- time per verified outcome;
- manual retry rate;
- preference/variant retention;
- recommendation result-observed rate;
- user trust/opt-out/reset.

### Layer 3 — Tenant operating maturity

Goal: turn repeated individual success into governed tenant capability.

Levers:

- workspace/brand/activity profiles;
- role templates and delegation;
- shared tenant connections;
- scoped variants;
- standard workflows and quality validators;
- readiness and policy dashboards.

Metrics:

- ready workflows per workspace/brand/activity;
- policy conflict rate;
- approval turnaround;
- certified integration coverage;
- tenant-wide workflow success;
- reuse of proven profiles/variants.

### Layer 4 — Business outcome growth

Goal: improve configured business objectives.

Levers:

- activity-specific workflows and metrics;
- outcome attribution to effective manifests;
- experiments and canaries;
- next-best actions ranked by expected net value;
- closed-loop result observation.

Metrics vary by activity:

- SEO visibility/qualified traffic;
- leads and conversion;
- revenue and average order value;
- retention and repeat purchase;
- campaign efficiency;
- content quality and publishing throughput;
- operational cost and reliability.

### Layer 5 — Platform capability growth

Goal: improve shared assets and defaults from certified reusable evidence.

Levers:

- capability-gap detection;
- privacy-safe promotion candidates;
- shared asset versioning;
- new connector/tool/workflow proposals;
- improved policy templates and onboarding;
- calibration and reliability feedback.

Metrics:

- gap-to-certified-capability lead time;
- shared asset adoption and verified success;
- rollback/defect rate by version;
- tenant-specific customization reduced by improved defaults;
- promotion candidate quality;
- platform-wide calibration.

## 4. Growth state model

Each tenant/workspace/brand/activity can be classified without hiding detail:

```text
unconfigured
→ discoverable
→ authorized
→ connected
→ certified
→ repeatable
→ optimized
→ innovating
```

Definitions:

- **unconfigured:** membership exists but required context/readiness is missing;
- **discoverable:** relevant shared assets can be found;
- **authorized:** roles/grants/policies permit defined uses;
- **connected:** required tenant/user integrations are valid;
- **certified:** workflows/actions pass required tests;
- **repeatable:** verified successful executions occur consistently;
- **optimized:** profiles/preferences/variants improve measurable outcomes;
- **innovating:** tenant generates certified reusable patterns or platform candidates.

The dashboard shows supporting metrics and gaps, not a single opaque maturity score.

## 5. Opportunity detection

Opportunities derive from gaps between current and next state:

### Readiness gap

Asset is relevant and authorized but connection/certification is missing.

Recommendation: complete setup, not create a variant.

### Authority gap

Asset is relevant but role/grant/policy blocks it.

Recommendation: explain policy or request exact delegation/approval—not bypass.

### Relevance gap

Many authorized assets exist but user repeatedly selects a small subset.

Recommendation: personal ranking or focused composition profile.

### Quality gap

Workflow completes but verification or outcome is weak.

Recommendation: validator, variant, different workflow, or process change.

### Capability gap

Repeated intent is unmatched or requires unsupported action.

Recommendation: new workflow/tool/connector/platform candidate.

### Standardization gap

Multiple users independently create similar successful personal variants.

Recommendation: tenant-scoped profile/variant candidate after review.

## 6. Next-best-action strategy

The platform ranks actions across categories:

1. unblock safety/readiness;
2. achieve first or repeat verified value;
3. improve outcome/quality;
4. reduce cost/effort;
5. standardize reusable tenant practice;
6. propose platform capability growth.

The UI shows at most three, balancing impact, readiness, effort, risk, confidence, and diversity.

## 7. Personalization ladder

```text
Explicit preference
→ accepted recommendation
→ stable personal profile
→ personal variant
→ scoped tenant practice
→ privacy-reviewed platform candidate
→ shared platform version
```

Movement up the ladder is never automatic. Each transition has increasing evidence and governance requirements.

## 8. Tenant learning without tenant copying

Tenant learning is stored as:

- profile selections;
- preferences;
- scoped policy atoms;
- optional variants;
- connection/readiness state;
- effective manifests and outcomes;
- proposals and experiments.

It is not stored as duplicate copies of every platform asset.

## 9. Platform network effects with isolation

Safe network effects come from:

- aggregate readiness patterns;
- anonymous failure classes;
- policy/operator calibration;
- connector reliability;
- common capability gaps;
- sanitized and reviewed templates;
- shared version performance after release.

Unsafe network effects include copying tenant prompts, brand data, credentials, audiences, or proprietary workflows across tenants. These remain forbidden without explicit legal/governance basis and review.

## 10. Economic model

The architecture should support transparent commercial boundaries without coupling them to policy internals.

Possible entitlement dimensions:

- asset family availability;
- managed versus dedicated connections;
- execution quotas;
- advanced composition profiles;
- variant counts/version retention;
- experiment volume;
- premium connectors/models;
- support/governance features.

Rules:

- entitlement restricts availability; it does not rewrite policy semantics;
- users see why an asset is unavailable;
- commercial upgrades are not disguised as safety recommendations;
- quota and cost estimates are visible before consequential execution;
- optimization cannot prioritize platform revenue over declared user/business outcomes without disclosure.

## 11. Growth experiments

Experiment classes:

- onboarding sequence;
- catalog ranking;
- recommendation explanation;
- default personal profile;
- workflow/agent ranking;
- composition template;
- low-risk variant;
- connection setup guidance;
- approval workflow efficiency;
- shared asset version.

Every experiment declares primary outcome, guardrails, cohort, duration, minimum sample, stop criteria, and rollback.

## 12. Feedback channels

- explicit thumbs/reason codes;
- accept/dismiss/edit recommendation;
- workflow completion and verification;
- business result observation;
- setup abandonment;
- repeated manual override;
- support issue and blocker classification;
- policy conflict and approval delays;
- experiment rollback;
- shared asset version regression.

Feedback events should be structured and minimal. Free text is treated as untrusted content and not direct authority.

## 13. Governance of defaults

Defaults have large platform impact and require stronger evidence than optional recommendations.

A default change needs:

- target population and applicability;
- baseline and proposed behavior;
- measured benefit;
- safety and fairness review;
- compatibility impact;
- opt-out/reset path where appropriate;
- staged rollout;
- rollback;
- versioned decision record.

One tenant's success is insufficient evidence for a global default.

## 14. Capability gap pipeline

```text
unmatched/repeated intent
→ gap clustering
→ business and user impact estimate
→ existing shared asset search
→ build/integrate/configure recommendation
→ design proposal
→ certification and release
→ shared catalog publication
→ adoption/outcome monitoring
```

The pipeline prevents duplicate capabilities by checking existing assets and composition/variant solutions first.

## 15. Growth debt

Track debt categories:

- missing catalog mappings;
- unprojected context subjects;
- policy fields without semantics;
- legacy/contextual mismatches;
- readiness gaps;
- stale or conflicting variants;
- unobserved outcomes;
- uncalibrated recommendations;
- expired experiments;
- unresolved promotion candidates;
- deprecated authorities/clients.

Debt is prioritized by safety, affected users, blocked value, recurrence, and effort.

## 16. Operating cadence

### Continuous

- readiness and safety monitoring;
- event validation;
- recommendation and experiment guardrails;
- authority invalidation;
- provider/connector health.

### Weekly

- top blockers and opportunities;
- experiment status;
- recommendation calibration;
- variant conflicts;
- parity/adaptation debt.

### Monthly

- tenant maturity progression;
- business outcome realization;
- shared asset quality/version review;
- connection/certification health;
- privacy and opt-out trends.

### Release cycle

- platform promotion candidates;
- default changes;
- new asset/operator/connector governance;
- cutover/retirement decisions.

## 17. Success definition

The platform is growing well when:

- more users achieve verified value from shared assets with less setup;
- personalization improves relevance without authority confusion;
- tenants standardize successful practices without duplication explosion;
- business outcomes improve with credible attribution;
- failures and recommendations become better calibrated;
- reusable improvements strengthen shared assets through governed release;
- safety, isolation, trust, cost, and latency remain within guardrails.
