# OpenRouter Docs Agent Provider Contract

## Purpose

OpenRouter is the priority model provider candidate for AI-assisted documentation drafting because it exposes an OpenAI-compatible chat-completions interface that can route to many model backends while keeping one platform-controlled provider boundary.

This contract registers OpenRouter as a platform-managed provider candidate for the Docs Agent. It does **not** activate live provider dispatch by itself.

## Current status

```text
provider_key = openrouter_openai_compatible
primary_model_key = openrouter_docs_agent_writer_v1
review_model_key = openrouter_docs_agent_reviewer_v1
status = planned
credential_boundary = platform_managed
instruction_contract = docs_agent_openrouter_instruction_contract_v1
```

The provider remains planned until all of these are true:

1. A platform credential binding exists for `OPENROUTER_API_KEY` without exposing the value.
2. The platform bridge health route proves `secrets_included=false`.
3. The OpenAI-compatible bridge dry-run passes with `dry_run=true` and no provider dispatch.
4. Provider dispatch is enabled only through a scoped platform proxy.
5. `ai_model_providers` and `ai_model_registry` statuses are promoted to `active` only after same-cycle validation.
6. The governed `openrouter_provider_smoke` shell alias succeeds and returns `secrets_included=false`.

## Instruction bundle

Any OpenRouter-backed Docs Agent must receive the following instruction bundle before drafting:

- Use only the Growth Intelligence Platform governed API/orchestrator.
- Do not call OpenRouter directly from the agent.
- Do not request, output, or copy provider credentials.
- Read the docs impact manifest generated by `docs-impact-classifier.mjs`.
- Read bounded git diff and bounded target documentation snippets only.
- Follow `docs/change-documentation-governance.md` and `docs/ai-docs-agent-governance.md`.
- For deployment/runtime changes, consult `deployment_parity_checklist.md` and the Hostinger runtime sync runbook.
- Output a unified diff or structured docs patch plus concise rationale.
- Never merge its own PR; GitHub auto-merge remains branch-protection gated.

## Allowed tasks

```text
draft_docs_patch
review_docs_patch
explain_docs_impact
suggest_required_doc_targets
```

## Forbidden tasks

```text
deploy production
restart services
mutate live database
read or output credentials
approve own PR
bypass branch protection
perform native GitHub mutations directly from the model
```

## Model profile

The registry stores two planned model profiles:

- `openrouter_docs_agent_writer_v1` for drafting documentation patches.
- `openrouter_docs_agent_reviewer_v1` for reviewing documentation patches and required-doc coverage.

The default model slug is stored as `~openai/gpt-latest` with `openai/gpt-4o-mini` as a cost-aware fallback. These are registry hints only; the runtime orchestrator must check current availability, cost policy, and credential status before dispatch.

## Secret boundary

The model provider contract records `secrets_returned_to_agent=0`. The only allowed credential reference is an abstract platform binding key:

```text
credential_bindings:platform:openrouter_api_key
```

The actual API key must never be stored in docs, migration SQL literals, generated impact notes, model prompts, or agent output.

## Activation checklist

The migration also records `openrouter_provider_activation_checklist_v1` in `platform_runtime_config`. Operators should use that checklist to promote the provider from `planned` to `active` only after credential and bridge smoke evidence exists.
